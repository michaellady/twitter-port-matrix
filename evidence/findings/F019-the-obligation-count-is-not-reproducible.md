# F019 — The recorded obligation count is not reproducible, and most of what it counts is not an obligation

**Status:** found while running Go R4 for the first time in the cloud environment
**Class:** a count that looks like evidence — `FINDINGS.md` Pattern 1, third instance

## What was recorded

`CLOUD.md` pins the Go corner's R4 result as a fixed figure:

> **R4/Go** — 283 Viper members — is **Gobra v25.02**, pinned by image digest.

`spec/refinement/obligations.json` carries the same number with its companion:

> Viper members: 283 total, 133 with a body and verified.

The number is presented the way a version string is: something the pin makes
stable, such that a different result would mean a different tool.

## What eight runs actually produce

Same jar (sha256 `33d2dce5…`, from the pinned image digest `2ef080cc`), same
sources, same command:

| runs | distinct Viper members | with a body and verified |
|---|---|---|
| 5 of 8 | **238** | **134** |
| 2 of 8 | 237 | 133 |
| 1 of 8 | 236 | 132 |

The verdict lines are identical every time — `Gobra found no errors` for all
five packages, `Gobra has found 0 error(s)`. **The result is stable; the count
is not.**

## The mechanism, exactly

Diffing the reports of a 238-run against a 236-run leaves two members:

```
clock    $IMPORTS_73aaf354_ad177c4e   hasBody=true verified=true
ids      $IMPORTS_f1d0ae1d_993b844c   hasBody=true verified=true
```

`$IMPORTS_*` members are generated by Gobra to check that a package's imports
are well-defined. They are not obligations about this implementation, nobody
wrote them, and whether they are reported at all depends on which parallel
verification task reaches the shared dependency first. They are also counted as
*verified*, so the noise lands in both columns.

## The larger point: 61% of the count is scaffolding

Classifying all 238 members of one run by what generated them:

| category | total | verified |
|---|---|---|
| declared in the source | 147 | **52** |
| generated: termination proof | 38 | 38 |
| generated: `$IMPORTS` (import well-definedness) | 25 | 25 |
| generated: interface-implementation proof | 18 | 9 |
| generated: `$INIT` (package initialisation) | 10 | 10 |
| **total** | **238** | **134** |

Of the 134 "verified" members, **82 are compiler-generated scaffolding and 52
are declared in the source.** A termination proof is a real check, but it is
not one of F1–F9, and counting it alongside them is what makes 134 sound like
a measure of how much of the contract holds.

Ten of the 238 are in `stubs/` — the trusted model of the standard library —
and verify nothing at all (0 verified).

## Why this is F016 again, with a different cause

F016 found that Verus's "23 verified" was 11 units with no `ensures`, 11
conditional on assumed axioms, and one real property. The arithmetic differs
here and the shape does not: **the unit the tool counts is not the unit the
claim is about.** Verus counts units of work; Gobra counts Viper members. In
neither case does the number answer "how many properties of this code are
proved."

For the record, the unit that *is* about the contract: 146 `ensures` clauses,
of which 91 are functional obligations, 30 are permission framing, 13 are
assumed because their member is `// @ trusted`, and 12 are assumed because
their member is a body-less ghost declaration. **25 of the 146 are never
checked by Gobra at all.**

## Why 283 could not be reproduced

Not established. The gap is 45–47 members, far outside the ±2 observed
variance, so it is not the same effect. It is not the F018 fix either — that
commit changed `service` only, and re-running at S-13 (`4bc2706`, the commit
that recorded 283) gives 238/134, not 283/133. The most likely explanation is a
different counting convention over the same report — the raw task-row count,
which double-counts a member once per importing package, is 290 in the same
run — but no convention tried yields 283, and the original run's report was not
kept, so this is a hypothesis and is recorded as one.

## The rule

**A count from a tool is a measurement, not a constant, and it needs a range
and a decomposition before it means anything.** Two questions before recording
one:

1. *Does it reproduce?* Run it more than once. Here the answer was no, and one
   run would never have shown that.
2. *What is it counting?* Here, 61% of it is machine-generated and 4% is the
   trusted stdlib stub.

Recording "283 Viper members" next to a digest pin implies both answers are
yes. Both are no.
