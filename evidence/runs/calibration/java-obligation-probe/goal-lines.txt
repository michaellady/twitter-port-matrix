Java corner -- per-obligation JBMC probe, verbatim goal lines
=============================================================

How this was produced (reproducible from the repository root):

    C=<scratch>/classes; JUTIL=<scratch>/jutil
    javac --release 17 -nowarn -d $C $(find impls/java/src impls/java/verification -name '*.java')
    jbmc --classpath "$C:/usr/lib/core-models.jar:$JUTIL" twitterport.verification.<Class> \
         --function 'twitterport.verification.<Class>.<fn>:<sig>' \
         --unwind 30 --max-nondet-string-length 3 --java-assume-inputs-non-null

$JUTIL is java.util extracted with `jimage extract` from
/usr/lib/jvm/java-21-openjdk-amd64, exactly as tools/cmd/jbmc does it.
jbmc 6.11.0 (cbmc-6.11.0), javac 21.0.10 with --release 17.

Every obligation and every canary was run BEFORE any Blocked reason was written
down, so the java table in tools/cmd/jbmc/obligations.go is a record of this run
rather than a copy of the Kotlin corner's. These transcripts are from a re-run
against the committed sources, so the line numbers below are the ones in
impls/java/verification/twitterport/verification/.

Only the entry point's OWN assertion goals are quoted. JBMC's inserted checks
(null-pointer, divide-by-zero, "no uncaught exception") decide nothing, and
neither do assertion goals inside java.lang, java.util or org.cprover -- a
library goal says something about JBMC's model of the JDK, not about the port.
That is the accounting tools/cmd/jbmc/run.go applies (goalLine, `own`), and it
is applied here so the two agree.

The four entries showing "SAT checker ran out of memory" were run under an
artificial `ulimit -v 8000000`; see the uncapped section at the end, which is
the evidence that actually establishes the wall.

The two SAT-exhausting entry points, uncapped
---------------------------------------------
A `ulimit -v` proves only that a cap can be hit. Two of the four were re-run
with NO cap at all on a 15 GB machine, and the kernel's own report is the
evidence:

    Memory cgroup out of memory: Killed process 2811 (jbmc)
      total-vm:16420540kB, anon-rss:13951040kB, file-rss:4528kB

    c4_pageMayExceedLimit   EXIT=137 WALL=228s   (uncapped, OOM-killed at 13.9 GB RSS)
    o4a_pageRespectsLimit   EXIT=137 WALL=57s    (uncapped, OOM-killed)

So satReason on this corner is a machine-level wall rather than an induced one.
The Kotlin entry in tools/cmd/jbmc/obligations.go records 11 GB; this corner
wants more.


The getBytes defect, probed directly
------------------------------------
`assert X` and `assert !X` were each run as their own entry point over a
standalone class compiled against impls/java's Dom. BOTH failing means the
predicate is NONDETERMINISTIC -- the exact dual of the vacuity signature (both
succeeding), and the reason a getBytes-blocked obligation must not be scored as
a kill either. F037 is what that costs the rung as it stands.

    vh_alice_true    assert Dom.validHandle("alice")                    -> FAILURE
    vh_alice_false   assert !Dom.validHandle("alice")                   -> FAILURE
    vh_EVE_true      assert Dom.validHandle("EVE")                      -> FAILURE
    vh_EVE_false     assert !Dom.validHandle("EVE")                     -> SUCCESS
    vh_empty_true    assert Dom.validHandle("")                         -> FAILURE
    vh_empty_false   assert !Dom.validHandle("")                        -> SUCCESS
    vt_empty_true    assert Dom.validText("")                           -> FAILURE
    vt_empty_false   assert !Dom.validText("")                          -> FAILURE
    len_alice        assert "alice".getBytes(UTF_8).length == 5         -> FAILURE
    len_alice_not    assert "alice".getBytes(UTF_8).length != 5         -> FAILURE
    byte0_alice      assert "alice".getBytes(UTF_8)[0] == (byte)'a'     -> FAILURE
    byte0_alice_not  assert "alice".getBytes(UTF_8)[0] != (byte)'a'     -> FAILURE

Read the last four rows first: the byte array `getBytes` returns has neither a
determined length nor determined contents. Everything above follows from that.
Why JBMC nonetheless decides `!validHandle("EVE")` and not `validHandle("alice")`
is NOT pinned here and is not claimed -- the measurements are.
